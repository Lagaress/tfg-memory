    \noindent Esta parte describe el desarrollo de la aplicación móvil Dixi, que integra los motores de generación de oraciones con una interfaz accesible basada en pictogramas y un motor de síntesis de voz.

\chapter{Aplicación Móvil}
\label{ch:aplicacion-movil}

Los capítulos anteriores han descrito tres técnicas de generación de oraciones y tres hibridaciones que las combinan. Cada una existe como un módulo Python independiente con su propia lógica, sus dependencias y sus pruebas. La aplicación móvil Dixi es la pieza que conecta estos motores con las personas que los necesitan: una interfaz táctil donde el usuario selecciona pictogramas, el sistema genera una oración y la reproduce como voz.

El reto de esta capa no es lingüístico sino de diseño e ingeniería. Los usuarios de CAA tienen perfiles muy diversos: personas con Trastorno del Espectro Autista, parálisis cerebral, afasia, ELA u otras condiciones que dificultan el habla. La interfaz debe ser accesible para todos ellos, lo que implica retroalimentación visual y háptica, tamaños ajustables, contraste adecuado y una organización de pictogramas que permita construir mensajes con el menor número posible de toques.

La arquitectura sigue un modelo cliente-servidor. La app móvil, desarrollada con React Native~\cite{reactnative2024} y Expo~\cite{expo2024}, actúa como cliente: presenta el tablero de pictogramas, recoge la selección del usuario y muestra la frase generada. Un servidor FastAPI~\cite{fastapi2024} actúa como puente entre la app y los motores de generación, que están escritos en Python y no pueden ejecutarse en un dispositivo móvil. Esta separación permite que la app sea ligera mientras el procesamiento pesado ocurre en el servidor.

El capítulo recorre primero las decisiones tecnológicas que llevaron a esta arquitectura, luego describe el diseño del servidor y sus adaptadores de motores, después la interfaz de usuario con sus tres pantallas y la gestión del estado, y cierra con el diseño accesible y la síntesis de voz.

\section{Decisiones tecnológicas}
\label{sec:app-tecnologias}

La elección de React Native~\cite{reactnative2024} como framework de la app responde a la necesidad de cubrir iOS y Android desde un único código fuente. El proyecto usa React Native 0.81 con React 19, compilado mediante el SDK de Expo 54~\cite{expo2024}. Expo aporta un conjunto de bibliotecas nativas preconfiguradas (cámara, audio, hápticos, almacenamiento) y un sistema de compilación que abstrae la configuración de Xcode y Gradle. La navegación se gestiona con Expo Router 6, que organiza las pantallas como ficheros en un directorio, de forma análoga a Next.js en el entorno web. La app tiene habilitada la \textit{New Architecture} de React Native, que emplea el motor Hermes para la ejecución de JavaScript y un sistema de renderizado más eficiente. Todo el código del cliente está escrito en TypeScript 5.9, lo que añade tipado estático sobre JavaScript y reduce una categoría frecuente de errores en tiempo de ejecución.

El servidor usa FastAPI~\cite{fastapi2024}, un framework web para Python. La elección viene condicionada por los motores de generación: los tres están escritos en Python y dependen de bibliotecas que no existen en otros lenguajes. La gramática formal usa Lark~\cite{lark2024} como \textit{parser} de la CFG. El motor de embeddings carga el modelo FastText \texttt{cc.es.300.bin}~\cite{bojanowski2017fasttext}, un fichero binario de 6,7 GB que se mapea directamente en memoria. El motor de LLMs utiliza el SDK de OpenAI para Python. Portar cualquiera de estos componentes a TypeScript o Go habría supuesto reescribirlos desde cero, y alternativas como AWS Lambda quedaban descartadas porque el modelo FastText excede los límites de memoria de las funciones \textit{serverless}. FastAPI ofrece soporte nativo para \texttt{async/await}, documentación OpenAPI generada automáticamente y un mecanismo de \textit{lifespan} para cargar recursos pesados una sola vez al arrancar el servidor.

La decisión de interponer un servidor entre la app y los motores tiene una motivación adicional de seguridad. El motor de LLMs requiere una clave de API de OpenAI. Si la app llamase directamente a la API de OpenAI, esa clave tendría que estar embebida en el binario de la aplicación (APK en Android, IPA en iOS), donde sería extraíble mediante ingeniería inversa. Con el servidor como intermediario, la clave reside exclusivamente en el entorno del servidor y la app nunca la conoce.

El frontend utiliza varias bibliotecas especializadas para cubrir los requisitos de rendimiento y accesibilidad de una app de CAA. La carga de imágenes de pictogramas usa \texttt{expo-image}, que implementa caché en disco y reciclaje de vistas para evitar picos de memoria al desplazar la cuadrícula. Las animaciones de retroalimentación táctil emplean \texttt{react-native-reanimated} 4.1, que ejecuta las animaciones en el hilo nativo de la interfaz para mantener 60 fotogramas por segundo. La síntesis de voz se integra mediante \texttt{expo-speech} 14.0, que expone los motores nativos de cada plataforma (AVSpeechSynthesizer en iOS, TextToSpeech en Android). La retroalimentación háptica utiliza \texttt{expo-haptics} 15.0, y las listas de alto rendimiento emplean \texttt{@shopify/flash-list} 2.0 en lugar del FlatList estándar de React Native.

\section{Arquitectura del sistema}
\label{sec:app-arquitectura}

El flujo de comunicación completo atraviesa cuatro etapas. El usuario selecciona pictogramas en el tablero de la app. La app extrae las etiquetas textuales de los pictogramas seleccionados y las envía al servidor como una lista de cadenas de texto. El servidor delega la generación al motor configurado y devuelve la frase resultante. La app muestra la frase y, si el usuario lo solicita, la reproduce como voz. Un ejemplo concreto: el usuario toca los pictogramas ``yo'', ``querer'' y ``agua''; la app envía una petición POST al endpoint \texttt{/generate} con el cuerpo \texttt{\{"pictograms": ["yo", "querer", "agua"]\}} y el parámetro \texttt{engine=grammar}; el servidor responde con \texttt{\{"sentence": "Yo quiero agua", "engine": "grammar", "processing\_time\_ms": 0.45, "success": true\}}; la app muestra ``Yo quiero agua'' en la barra de construcción.

El servidor organiza los motores de generación mediante dos patrones complementarios: \textit{Strategy} y \textit{Registry}. Todos los motores implementan una clase base abstracta \texttt{GenerationEngine} que define tres métodos: \texttt{setup()} para la carga de recursos (modelo FastText, conexión a OpenAI, etc.), \texttt{generate(pictograms)} que recibe la lista de pictogramas y devuelve un \texttt{GenerationResult}, y \texttt{name()} que devuelve el identificador del motor. \texttt{GenerationResult} es una clase de datos con seis campos: la oración generada, el nombre del motor, el tiempo de procesamiento en milisegundos, un indicador de éxito, un mensaje de error opcional y un diccionario de metadatos.

\texttt{EngineRegistry} mantiene un registro de clases y un diccionario de instancias. Al arrancar, lee la variable de entorno \texttt{ENGINES} (una lista de nombres separados por comas), instancia solo los motores indicados y ejecuta su método \texttt{setup()}. Las instancias se almacenan como singletons: cada motor se crea e inicializa una sola vez y atiende todas las peticiones posteriores. Para añadir un motor nuevo basta con crear una clase que herede de \texttt{GenerationEngine}, registrarla en el \textit{registry} e incluir su nombre en la variable de entorno; no es necesario modificar el código del servidor ni de los demás motores.

El servidor no reimplementa la lógica de generación. Cada adaptador inserta en el \texttt{sys.path} de Python la ruta del directorio donde reside la técnica correspondiente (por ejemplo, \texttt{techniques/formal-grammar/src/}) e importa directamente sus clases. El adaptador de gramática formal importa \texttt{SentenceGenerator} del módulo de gramática; el adaptador de embeddings importa \texttt{HybridGenerator} del módulo de embeddings; el adaptador de LLMs importa \texttt{LLMEngine} del módulo de modelos de lenguaje. Las técnicas se mantienen intactas, con sus tests y sus interfaces originales. El servidor es una capa de orquestación que traduce peticiones HTTP a llamadas a estos generadores y empaqueta los resultados en un formato uniforme.

\section{Servidor de generación}
\label{sec:app-servidor}

El servidor consta de 497 líneas de Python organizadas en tres módulos. El módulo raíz contiene el punto de entrada (\texttt{main.py}), la configuración (\texttt{config.py}) y los esquemas de datos (\texttt{schemas.py}). El módulo de motores (\texttt{engines/}) contiene la clase base abstracta, el registro y los seis adaptadores: gramática, embeddings, LLM, y las tres hibridaciones. El módulo de rutas (\texttt{routes/}) define los endpoints HTTP. La configuración usa Pydantic Settings para leer variables de entorno con valores por defecto: \texttt{ENGINES} (por defecto \texttt{"grammar"}), \texttt{OPENAI\_API\_KEY}, \texttt{FASTTEXT\_MODEL\_PATH}, \texttt{HOST}, \texttt{PORT} y \texttt{GENERATION\_TIMEOUT\_SECONDS}.

El endpoint principal es \texttt{POST /generate}. Recibe un cuerpo JSON con una lista de pictogramas (entre 1 y 20 etiquetas) y un parámetro de consulta \texttt{engine} que indica qué motor usar, con \texttt{"grammar"} como valor por defecto. La generación se ejecuta en un \textit{thread pool} mediante \texttt{asyncio.wait\_for()} con un \textit{timeout} configurable de 30 segundos. Si el motor solicitado no está disponible en el registro, el servidor devuelve HTTP 400. Si la generación excede el \textit{timeout}, devuelve HTTP 408. El servidor expone dos endpoints de salud: \texttt{GET /health}, que devuelve un simple indicador de que el proceso está vivo, y \texttt{GET /health/ready}, que verifica que al menos un motor esté cargado y devuelve la lista de motores disponibles; si ninguno está operativo, responde HTTP 503.

Los seis adaptadores encapsulan los motores descritos en capítulos anteriores. El adaptador de gramática envuelve el \texttt{SentenceGenerator} de la gramática formal (capítulo~\ref{ch:gramatica-formal}); no tiene dependencias externas y responde en menos de un milisegundo, lo que lo convierte en la opción más rápida y en la única que funciona completamente offline. El adaptador de embeddings envuelve el \texttt{HybridGenerator} del motor de embeddings semánticos (capítulo~\ref{ch:enfoque-hibrido}); requiere cargar el modelo \texttt{cc.es.300.bin} de FastText en memoria (6,7 GB) y responde entre 100 y 200 milisegundos, también sin conexión a Internet. El adaptador de LLM utiliza el SDK de OpenAI para enviar peticiones a GPT-4o-mini (capítulo~\ref{ch:modelos-lenguaje}); su latencia oscila entre 500 y 2.000 milisegundos y requiere conexión a Internet. Los tres adaptadores de hibridación (capítulo~\ref{ch:hibridacion}) combinan los motores base: la Hibridación 1 (gramática + LLM como post-editor) y la Hibridación 2 (embeddings + LLM como post-editor) tienen latencias similares al motor de LLM, mientras que la Hibridación 3 (\textit{overgenerate-and-rank}) genera candidatas con los tres motores base, las filtra por cobertura semántica y las ordena por perplejidad usando MariaGPT-2, con tiempos de respuesta entre 200 y 3.500 milisegundos según cuántos motores estén activos.

La gestión de recursos descansa en el mecanismo de \textit{lifespan} de FastAPI. Al arrancar el servidor, un gestor de contexto asíncrono recorre los motores configurados e invoca su método \texttt{setup()}, que carga en memoria los recursos necesarios: el modelo FastText, las gramáticas de Lark, los modelos de perplejidad. Estos recursos permanecen en memoria durante toda la vida del proceso y se comparten entre todas las peticiones. El modelo FastText, con sus 6,7 GB, se carga una sola vez; sin este mecanismo, cada petición tendría que cargarlo de nuevo, lo que haría inviable el servicio.

La clave de API de OpenAI reside exclusivamente en el archivo \texttt{.env} del servidor. La app móvil no la contiene, no la transmite y no la necesita: envía las etiquetas de pictogramas al servidor y recibe la frase generada, sin conocer qué motor la produjo ni qué credenciales se usaron. El servidor habilita CORS con \texttt{allow\_origins=["*"]} para facilitar el desarrollo. No implementa autenticación de API propia, una simplificación aceptable en un proyecto académico donde el servidor se ejecuta en red local.

El manejo de errores sigue una estrategia de degradación. Si un motor falla durante la generación, el adaptador devuelve un \texttt{GenerationResult} con \texttt{success=false} y el mensaje de error, en lugar de propagar una excepción HTTP 500. Esto permite que la app distinga entre un fallo del servidor (que requiere reintentar) y un fallo del motor (que puede gestionarse mostrando un mensaje al usuario o recurriendo al generador local de la app como respaldo).

\section{Interfaz de usuario}
\label{sec:app-interfaz}

La app organiza sus tres pantallas mediante una barra de pestañas inferior, el patrón de navegación estándar en aplicaciones móviles de uso frecuente. La navegación usa Expo Router con rutas basadas en ficheros: cada archivo \texttt{.tsx} en el directorio de pestañas corresponde a una pantalla.

La pantalla principal es el tablero de comunicación, el espacio donde el usuario construye mensajes seleccionando pictogramas. En la parte superior, una barra de construcción muestra en \textit{scroll} horizontal los pictogramas que el usuario ha ido seleccionando, con la frase generada debajo. Tocar un pictograma en esta barra lo elimina de la selección, permitiendo corregir sin empezar de nuevo. Debajo de la barra de construcción, un campo de búsqueda con un \textit{debounce} de 150 milisegundos permite filtrar el catálogo de pictogramas por nombre: el usuario escribe ``agu'' y solo aparecen los pictogramas cuyo nombre contiene esa cadena.

Una barra de categorías muestra las nueve categorías del catálogo como píldoras horizontales con los colores del sistema de FitzGerald~\cite{fitzgerald1949straight}, un código cromático estándar en CAA que asigna un color a cada categoría gramatical: naranja para personas, verde para acciones, rosa para necesidades, naranja oscuro para objetos, azul para lugares, morado para cualidades, rojo para emociones, marrón para tiempo y gris para preguntas. El cuerpo de la pantalla muestra los pictogramas en una cuadrícula configurable de tres a cinco columnas. Cada tarjeta muestra la imagen del pictograma cargada desde el CDN de ARASAAC~\cite{arasaac} y su etiqueta textual. Al tocar una tarjeta, una animación \textit{spring} (escala de 1 a 0,93 y retorno) proporciona retroalimentación visual inmediata, acompañada opcionalmente de vibración háptica. Dos botones flotantes completan la pantalla: uno para añadir pictogramas personalizados (nombre, categoría y opcionalmente imagen) mediante un modal, y otro para reproducir la frase generada con síntesis de voz. El catálogo incluye más de 200 pictogramas ARASAAC organizados en las nueve categorías, más una categoría ``Todas'' que los muestra sin filtrar.

La segunda pantalla contiene frases predefinidas para comunicación rápida. El usuario no necesita componer pictogramas: toca una frase y el sistema la reproduce directamente. Las frases se organizan por contexto de uso (casa, colegio, médico, social, emociones) en una lista con secciones colapsables. Cada frase tiene un botón de reproducción y un indicador de favorito. El usuario puede añadir frases propias a una sección personal (``Mis frases'') y buscar entre todas las frases con filtrado en tiempo real. Esta pantalla complementa al tablero de comunicación: el tablero permite construir mensajes nuevos con pictogramas, mientras que las frases predefinidas cubren expresiones de uso frecuente que el usuario quiere tener siempre a mano.

La tercera pantalla agrupa los ajustes de la aplicación. La sección de voz permite seleccionar una voz del sistema (filtrada a voces en español), ajustar la velocidad de habla entre 0,5x y 2,0x y modificar el tono entre 0,5 y 2,0, con un botón para probar la configuración antes de aplicarla. La sección de apariencia controla el modo claro u oscuro, el tamaño de los pictogramas (pequeño, mediano o grande) y el número de columnas de la cuadrícula. La sección de accesibilidad permite activar o desactivar la vibración háptica y los efectos de sonido, y ajustar el tamaño de fuente entre 14 y 22 píxeles. La pantalla cierra con una sección informativa que muestra el logotipo de Dixi, la versión de la aplicación y los créditos con un enlace a ARASAAC.

\section{Gestión del estado}
\label{sec:app-estado}

La app gestiona su estado mediante la Context API de React, con cinco contextos que envuelven la jerarquía de componentes desde el \textit{layout} raíz. Cada contexto encapsula un dominio funcional y expone tanto el estado como los métodos para modificarlo.

El contexto de tema gestiona el modo claro y oscuro. Almacena dos paletas completas de colores, incluyendo variantes de los colores de FitzGerald adaptadas a cada modo para mantener el contraste. El valor por defecto se toma de la preferencia del sistema operativo. El contexto de ajustes almacena todas las preferencias del usuario: la voz seleccionada, la velocidad y el tono de habla, el tamaño de los pictogramas, el número de columnas, la vibración háptica y el tamaño de fuente. Cada propiedad tiene su propio \textit{setter}, lo que permite que los controles de la pantalla de ajustes modifiquen valores individuales sin afectar al resto.

De los cinco, el contexto del tablero es el más complejo. Mantiene la lista de pictogramas seleccionados, la categoría activa, la consulta de búsqueda, los pictogramas personalizados, la frase generada y un indicador de si hay una generación en curso. Cuando la lista de pictogramas seleccionados cambia, un \texttt{useEffect} con un \textit{debounce} de 300 milisegundos dispara automáticamente una petición al servidor. Para evitar condiciones de carrera, cada petición recibe un identificador único mediante una referencia (\texttt{requestIdRef}). Cuando llega una respuesta, el contexto compara el identificador de la petición con el último identificador emitido; si no coinciden, la respuesta pertenece a una petición obsoleta y se descarta. Solo se procesa la respuesta cuyo identificador coincide con el actual, garantizando que la frase mostrada siempre corresponda a la selección más reciente del usuario.

Si la petición al servidor falla por caída de red o \textit{timeout}, el sistema recurre a un generador local implementado en el propio código de la app. Este generador contiene más de 60 correspondencias directas entre combinaciones de pictogramas y frases conjugadas, además de una tabla de conjugación para 11 verbos en 4 personas gramaticales. No pretende replicar la calidad de los motores del servidor, pero garantiza que el usuario siempre reciba una respuesta: en una herramienta de comunicación, el silencio no es una opción aceptable.

El contexto de frases gestiona las secciones de frases predefinidas, los favoritos del usuario y la búsqueda. El contexto de notificaciones proporciona mensajes \textit{toast} en la parte inferior de la pantalla, con \textit{auto-dismiss} a 2,5 segundos y animación de \textit{fade}.

\section{Diseño accesible}
\label{sec:app-accesibilidad}

La interfaz de una aplicación de CAA no puede tratarse como la de una app convencional. Los usuarios que dependen de pictogramas para comunicarse tienen, con frecuencia, dificultades motoras o visuales que condicionan cómo interactúan con una pantalla táctil. Las decisiones de diseño de Dixi priorizan la accesibilidad en tres ejes: organización visual, retroalimentación multisensorial y adaptabilidad.

La organización visual del catálogo de pictogramas sigue el sistema cromático de FitzGerald descrito en la sección~\ref{sec:app-interfaz}. La app implementa este código con dos variantes, una para tema claro y otra para tema oscuro. En tema claro, las acciones (verbos) se representan en verde (\texttt{\#448361}), las personas en naranja (\texttt{\#E08B3A}), las necesidades en rosa (\texttt{\#D45C8A}), los objetos en naranja oscuro (\texttt{\#C7722E}), los lugares en azul (\texttt{\#5B8FB9}), las cualidades en morado (\texttt{\#8B6BAE}), las emociones en rojo (\texttt{\#D15B5B}) y el tiempo en marrón (\texttt{\#8B7355}). Los valores para el tema oscuro se ajustan para mantener ratios de contraste adecuados sobre fondos oscuros. El código cromático no es solo decorativo: permite al usuario localizar rápidamente la categoría que busca sin necesidad de leer las etiquetas, una ventaja para personas con dificultades lectoras.

La retroalimentación al usuario opera en tres canales simultáneos. El canal visual proporciona animaciones \textit{spring} al seleccionar pictogramas y transiciones de color al cambiar de categoría. El canal háptico genera vibración táctil configurable (impacto ligero o medio) en cada interacción significativa: seleccionar un pictograma, eliminarlo de la barra de construcción, cambiar de categoría. El canal auditivo reproduce la frase generada mediante síntesis de voz. Los tres canales son independientes y configurables: el usuario puede desactivar la vibración o los efectos de sonido desde los ajustes sin afectar a los demás.

La adaptabilidad de la interfaz se concreta en varios controles. El tamaño de fuente es ajustable entre 14 y 22 píxeles mediante un deslizador, lo que beneficia a usuarios con dificultades visuales. El número de columnas de la cuadrícula (de 3 a 5) permite que cada usuario encuentre el equilibrio entre tamaño de pictograma y cantidad visible. El modo oscuro, además de reducir la fatiga visual, emplea paletas diseñadas para mantener contraste WCAG. Todos los elementos interactivos incluyen \texttt{accessibilityLabel} y \texttt{accessibilityRole} para lectores de pantalla, y las pestañas de navegación reportan su estado de selección con \texttt{accessibilityState}. La app utiliza \texttt{useSafeAreaInsets()} para que el contenido no quede oculto por el \textit{notch}, la barra de estado o el indicador \textit{home} en dispositivos modernos.

\section{Síntesis de voz}
\label{sec:app-tts}

La síntesis de voz es la etapa final del flujo de comunicación. La frase generada a partir de los pictogramas se reproduce como audio para que el interlocutor la escuche, cerrando el ciclo que empieza con la selección de pictogramas y termina con la emisión de un mensaje audible. La app integra \texttt{expo-speech} 14.0, que da acceso a los motores nativos de síntesis de cada plataforma: AVSpeechSynthesizer en iOS y TextToSpeech en Android. La pantalla de ajustes permite seleccionar una voz en español de entre las disponibles en el dispositivo, ajustar la velocidad de habla y modificar el tono.

La integración completa de un motor de síntesis de voz de alta calidad queda como trabajo futuro. Los motores nativos de iOS y Android producen una voz funcional pero con una prosodia que difiere perceptiblemente del habla humana. La voz que recibiría un usuario final debería proceder de un motor de síntesis neuronal (servicios como ElevenLabs o modelos VITS~\cite{kim2021vits}) capaz de producir locuciones más naturales y expresivas. La versión actual del prototipo usa el motor nativo como solución provisional, pero la arquitectura de la app está preparada para esta evolución: los ajustes de voz, el botón de reproducción y el flujo de datos desde la frase generada hasta la salida de audio son genéricos y no dependen del motor subyacente. Conectar un servicio externo de TTS requerirá añadir una ruta en el servidor y sustituir la llamada a \texttt{expo-speech} por una petición HTTP que reciba el audio, sin alterar la interfaz ni la experiencia del usuario.
